❓ 8. Dúvidas Frequentes

🌐 9. Ambientes: Teste vs Produção

Existem duas pastas no servidor interno. O APK é uma WebView que carrega os arquivos de uma delas (definido no capacitor.config.json):

AmbienteURLFinalidade
Teste / Dev http://interno.progeral.com.br/Apps-testes/ Homologação — testar alterações antes de ir para produção
Produção http://interno.progeral.com.br/Apps-testes/ Ambiente real usado pelos operadores nos tablets

Onde alterar a URL que o APK carrega?

No arquivo capacitor.config.json, campo server.url:

{
  "server": {
    "url": "http://interno.progeral.com.br/Apps-testes/"
  }
}

Depois de alterar, precisa commitar, push e gerar um novo APK no Ionic Appflow.

⚠️ Atenção: O APK em si é um container vazio. Todo o conteúdo (HTML, CSS, JS, dados) é carregado ao vivo da URL configurada. Se você alterar arquivos no servidor, as mudanças aparecem imediatamente — sem precisar de APK novo.

Precisa ter dois APKs (teste + produção)?

Não necessariamente. Você pode ter um único APK apontando para o ambiente de teste, testar, e quando estiver tudo certo, copiar os arquivos para a pasta de produção. O APK continua o mesmo — só o conteúdo do servidor muda.

Mas se quiser dois APKs coexistentes nos tablets (um de teste, um de produção), você precisará de dois builds com capacitor.config.json diferentes (URLs diferentes) e appId diferentes no build.gradle.

Quais arquivos atualizar em cada ambiente?

Alterações de código (CSS/JS/HTML/PHP):

  • Teste: copiar para .../Apps-testes/
  • Produção: copiar para .../apontamento/
  • GitHub: push para versionar o código fonte

Alterações de dados (produtos.js, ops.js, recursos.js, motivos.js, zink-data.js):

  • Teste: copiar para .../Apps-testes/ (se quiser testar)
  • Produção: copiar para .../apontamento/
  • GitHub: não precisa — esses arquivos são carregados ao vivo do servidor. O GitHub só precisa deles se houver mudança na estrutura (ex: mudou o formato que o app.js lê os dados). Para atualizações rotineiras de dados (nova OP, novo produto), só o servidor basta.
💡 Fluxo recomendado para dados:
  1. Extraia os dados do ERP
  2. Copie os *.js para a pasta de produção (.../apontamento/)
  3. Pronto — os tablets já veem os dados novos na próxima atualização

📡 11. Monitor de Conexão

O app possui um indicador visual de conectividade que funciona em todas as telas:

IndicadorOnde apareceQuando ativa
🔴 Banner vermelho Topo fixo (todas as telas) Sem conexão com o servidor
🟡 Banner amarelo Topo fixo (todas as telas) Conexão lenta (2G ou RTT > 1s)
🟢 Pilula verde Header (Produção/Parada) Online
🔴 Pilula vermelha Header (Produção/Parada) Offline

Como funciona o Sensor de Offline agora (V1.5.0):

O aplicativo (agora embutido como APK) possui permissão nativa para interagir diretamente com o hardware de rede do tablet Android através da API HTML5 (navigator.onLine e listeners de janela).

  1. Disparo Instantâneo: Utilizamos window.addEventListener('offline'). No exato milissegundo em que a antena Wi-Fi do tablet perde o sinal (ou a placa de rede é desativada), o sistema operacional avisa o aplicativo e o banner vermelho cai na tela, sem depender de "tentar fazer uma requisição e falhar".
  2. Recuperação Automática: Usamos window.addEventListener('online'). Assim que o tablet se reconecta, o banner fica verde alertando "Conexão Restabelecida", oculta-se sozinho e a fila interna (se houver) já se prepara para sincronizar.

Diferente de versões antigas que faziam "ping" no servidor gastando bateria, essa abordagem escuta passivamente o hardware, sendo 100% precisa, instantânea e zero custo de processamento.

  1. navigator.onLine — API nativa do navegador/WebView
  2. Ping HTTP a cada 5s — faz um HEAD request em manifest.json com timeout de 3s. Se falhar, considera offline.

Isso garante que funcione corretamente mesmo no APK (Android WebView), onde o navigator.onLine sozinho é instável.

❓ 12. Dúvidas Frequentes

Preciso instalar Android Studio para atualizar?

Não. O Ionic Appflow compila o APK na nuvem. Você só precisa do Git e do navegador.

O que fazer se o build falhar?

Verifique se:

  • O arquivo .build/dist/index.html existe no repositório
  • Todos os arquivos foram commitados (git status limpo)
  • A branch correta está selecionada no Appflow

Preciso atualizar o versionCode sempre?

Sim, recomendado. Edite android/app/build.gradle e aumente o versionCode em 1 a cada atualização. O versionName segue o padrão semântico (ex: "1.4.6", "1.5.0").

As alterações no CSS/JS/dados aparecem sem APK novo?

Não. A aplicação é empacotada nativamente via Capacitor, ou seja, todos os arquivos (HTML, JS, CSS) ficam embutidos dentro do APK. Isso é vital para garantir que o app abra instantaneamente offline sem erros nativos do Android. Portanto, para qualquer alteração no visual (CSS) ou nas regras (JS), você precisa gerar um novo APK via Ionic Appflow.

Onde fica a comunicação com o Banco (Protheus)?

O aplicativo (que roda no tablet) se comunica obrigatoriamente usando URLs absolutas apontando para os arquivos PHP no seu servidor interno (http://interno.progeral.com.br/Apps-testes/api/...). Os scripts PHP (proxy.php, get_ops.php) servem como a ponte de comunicação que salva/lê no Protheus.

Guia Definitivo de Deploy (Colocar o app no ar)

Passo a passo rigoroso para atualizações:
  1. Commit no Github: Após fazer suas alterações e testar localmente, envie (commit e push) tudo para a branch main no Github.
  2. Atualizar o Servidor Apache: Baixe os novos arquivos (HTML/JS/PHP) na pasta do seu servidor (/var/www/Apps-testes/). Isso garante que os scripts de ponte do PHP estejam na versão mais atualizada e prontas para receber conexões.
  3. Gerar Novo APK no Ionic Appflow:
    • Acesse o Appflow.
    • Inicie um novo Build apontando para o último commit na branch main.
    • Escolha o Target Platform como Android e Build Type como Debug (ou Release).
    • Baixe o .apk gerado.
  4. Atualizar os Tablets: Desinstale o aplicativo antigo no tablet e instale este novo APK. (Desinstalar evita conflitos de cache do Service Worker).

O APK funciona fora da empresa?

Não. O APK aponta para uma URL interna (http://interno.progeral.com.br/Apps-testes/ ou http://interno.progeral.com.br/Apps-testes/), que só é acessível dentro da rede da Progeral.

4. Regras de Segurança: HTTPS e CORS

O aplicativo possui proteções rigorosas exigidas pelos navegadores modernos que afetam diretamente as requisições para a API (proxy.php). Ao realizar manutenção, atente-se às seguintes regras que foram implementadas para evitar falsos erros de "Sem Conexão":

  • Mixed Content (Conteúdo Misto): Como o servidor da Progeral (interno.progeral.com.br) utiliza certificado de segurança HTTPS, todas as chamadas de API feitas pelo aplicativo devem obrigatoriamente utilizar o prefixo https://. Injetar links http:// fará o navegador bloquear silenciosamente o envio de dados.
  • CORS Preflight (Requisições Cruzadas): Quando o aplicativo roda dentro do APK (sob domínio localhost), o envio para a API é considerado "Cross-Origin" (CORS). Não adicione cabeçalhos customizados (como Cache-Control ou Expires) na função fetch do app.js sem configurar o proxy.php para aceitá-los. Caso contrário, o servidor rejeitará a requisição preventiva (Preflight OPTIONS) e o envio será bloqueado.

Dica para desenvolvedores: Nunca altere o objeto API_CONFIG do app.js se você estiver trabalhando exclusivamente em regras de frontend (como monitor de rede ou interface). Mexa na API apenas se for expressamente necessário.
